# BUILD DIRECTIVE — Systematic Equity Research Platform (Paper-Trading Only)

**Mode:** Autonomous multi-session build with hard verification gates
**Repository:** `quant-research-platform` (this repository)

> This file is the verbatim build directive for this project. It is committed so that
> every session — which starts with zero context — can re-read the mission, the
> invariants, the gates, and the forbidden behaviors. Do not edit this file except to
> correct transcription errors. Scope changes go through `BACKLOG.md` and the human.

---

## 0. HOW TO OPERATE

You are the sole engineer on this project. You are building a production-grade systematic equity research platform with a full operator dashboard. You will work across many sessions. Assume you will lose all context between sessions and design accordingly.

### 0.1 State files — create these first, maintain them always

| File | Purpose |
|---|---|
| `PLAN.md` | Full phase breakdown, every task with an ID and status |
| `PROGRESS.md` | Append-only log: timestamp, task ID, what was done, tests run, result |
| `DECISIONS.md` | Every non-obvious engineering decision with the reasoning and rejected alternatives |
| `BLOCKERS.md` | Anything you cannot resolve without a human. Never guess past a blocker |
| `TESTING_LEDGER.md` | Every model configuration and strategy variant ever evaluated. Append-only. Never delete a row |

At the start of every session: read all five, determine the next unstarted task, continue. At the end of every task: update `PROGRESS.md` and commit.

### 0.2 Verification gates

Each phase ends with a gate. A gate is a set of tests that must pass. **You do not proceed past a failing gate.** If a gate cannot be passed, write the reason to `BLOCKERS.md`, stop that track, and move to an independent track if one exists. Never mark a gate passed by weakening its test.

### 0.3 Reasoning allocation

Use extended reasoning heavily for: bitemporal schema design, label construction mathematics, the portfolio optimizer, and every part of the validation framework in Phase 10. These are the components where a silent error invalidates the entire system and will not surface as a test failure.

Use normal effort for: connectors, CRUD endpoints, UI components, migrations, fixtures.

### 0.4 Commit discipline

One commit per completed task. Conventional commits. Message body states which tests were run and their result. Never commit with failing tests. Never commit secrets, API keys, `.env` files, or data files.

## 1. MISSION

Build a research platform that:

1. Ingests market, fundamental, and textual data with strict point-in-time integrity
2. Uses LLMs to convert unstructured documents into structured numeric features
3. Ranks equities cross-sectionally using a regularized gradient-boosted model
4. Constructs portfolios with realistic cost and turnover modeling
5. Validates results with overfitting-resistant statistics
6. Executes against a **paper account only**
7. Exposes all of the above through an operator dashboard with full configuration control, analytics, and audit trails

### 1.1 Non-goals — do not build these

- Live trading with real capital. No code path may place a real order. This is not configurable
- Leverage, margin, options, futures, crypto
- Intraday or sub-daily strategies
- Neural network predictors, transformer price models, reinforcement learning
- Any LLM component that outputs a buy/sell decision
- Social sentiment scraping, Reddit/Twitter feeds
- Mobile apps, user registration, multi-tenancy, billing

If you find yourself building something not in section 1, stop and re-read this section.

### 1.2 Scope discipline

Feature requests that arrive mid-build go to `BACKLOG.md`, not into the code. A finished twelve-phase system beats a half-finished twenty-phase system. Every hour spent on an unrequested feature is an hour not spent on test coverage.

## 2. NON-NEGOTIABLE INVARIANTS

These are enforced by tests, not by convention. Each gets a property-based test suite.

**I1 — Temporal integrity.** No query may return a fact whose `knowledge_time` is later than the query's `as_of` timestamp. This is the single most important property in the system. Violating it produces backtests that look excellent and are worthless.

**I2 — Reproducibility.** Any result must be regenerable from: git commit + data version + config hash + seed. Store all four with every artifact.

**I3 — No fabricated data.** Never generate synthetic data and present it as real. Never stub a function to return plausible values. If a data source is unavailable, the system raises an error. A missing connector is a blocker, not an excuse for a mock.

**I4 — Cost realism.** No backtest result is reported gross. Every reported number is net of modeled spread, commission, impact, and borrow.

**I5 — Secret isolation.** API keys are encrypted at rest, never logged, never returned in full by any endpoint, never committed.

**I6 — Test honesty.** A test that is skipped, marked xfail, or weakened to pass counts as a failure. Delete a bad test or fix the code; never neuter it.

## 5. PHASES

Each phase lists deliverables, then the gate. Gates are binary.

### Phase 1 — Foundation

Docker Compose bringing up Postgres+TimescaleDB, Redis, backend, frontend. Config via Pydantic Settings. Structured JSON logging with correlation IDs. Alembic wired. CI running lint, typecheck, and tests on every push. Health endpoint.

**Gate:** `docker compose up` produces a working stack from a clean clone. CI green.

### Phase 2 — Bitemporal store

This is the foundation. Take your time.

Every fact table carries `valid_from`, `valid_to`, `knowledge_time`. A single query layer function `as_of(session, as_of_ts)` returns a scoped session; all downstream reads go through it and cannot bypass it. Hypertables on time-series tables. Indices designed for the as-of access pattern.

**Gate:** Hypothesis test generates random facts with random knowledge times, random as-of queries, and asserts across 10,000 cases that no returned row has `knowledge_time > as_of`. Zero failures. Additionally: a test proving that direct table access outside the query layer is impossible from application code.

### Phase 3 — Data ingestion

Connectors, each with retry, rate limiting, incremental sync, and a data-quality report:

- Daily OHLCV with full adjustment history
- Point-in-time fundamentals, unrestated, with original report dates
- SEC EDGAR filings using **acceptance timestamps**, not filing dates
- Earnings call transcripts
- Corporate actions: splits, dividends, delistings, ticker changes, M&A
- Borrow availability and rates
- Macro series

The corporate actions connector is mandatory and must include delisted securities. Without it every backtest is survivorship-biased and meaningless.

**Gate:** For a fixed historical date, the system reconstructs a price and fundamental snapshot that matches an independently sourced reference to within tolerance. Delisted names present. Data-quality report shows coverage, gaps, and staleness per source.

### Phase 4 — Universe construction

Point-in-time universe per rebalance date: ADV floor, price floor, market-cap floor, borrow-availability filter, exchange filter. Reconstructed historically — never using present-day membership.

**Gate:** Universe on a past date contains names later delisted. Universe size and turnover plotted over history and manually inspected for discontinuities.

### Phase 5 — Feature library

Baseline factors — momentum 12-1, book-to-price, earnings yield, gross profitability, ROIC, accruals, asset growth, low volatility, size, short interest, Amihud illiquidity.

Transform pipeline: winsorize 1/99 → cross-sectional z-score → sector neutralize → optional beta neutralize. Every feature declares its availability lag and the pipeline enforces it.

**Hard cap: 30 features total, including LLM features from Phase 7.** Adding a 31st requires removing one and logging the swap in `DECISIONS.md`.

**Gate:** Known factor premia reproduce with the correct sign and plausible magnitude over long samples. Feature correlation matrix reviewed for redundancy. No feature uses data unavailable at its stated timestamp.

### Phase 6 — Labels

Triple-barrier labeling: upper barrier, lower barrier, vertical (time) barrier, sized by trailing volatility. Returns residualized against market and sector. Sample-uniqueness weights computed from label overlap. Horizons: 5d, 21d, 63d.

**Gate:** Label distribution sane across regimes. Uniqueness weights sum correctly. A test proving that overlapping labels receive down-weighting, with the effect on effective sample size reported.

### Phase 7 — LLM extraction pipeline

Pipeline: document → chunk → **anonymize** (mask company names, tickers, executive names; strip all dates) → parallel extraction across an ensemble of 2–3 models → schema validation → median aggregation → disagreement score → store with prompt version hash.

Extract deltas, not states. Examples: change in risk-factor language between consecutive filings, guidance tone relative to guidance magnitude, evasiveness in analyst Q&A, accounting-language shifts, added and removed risk factors.

Required components:

- **Golden set:** 300–500 human-labelled documents as a permanent regression suite. Any prompt change re-runs it and the score is recorded
- **Contamination probe:** every document scored anonymized and named. Systematic divergence means the model is recalling outcomes rather than reading text. This runs in CI and gates deployment
- **Caching** keyed on `hash(document + prompt_version + model)`
- **Cost governor:** hard daily spend cap per provider, enforced before the call, not after
- **Temperature 0** everywhere. Raw responses stored

Extraction models must be cost-tier, not frontier. Frontier models here are a budget error on a reading-comprehension task.

**Gate:** Golden-set agreement ≥ 85% for the chosen ensemble. Contamination probe divergence below threshold and documented. Full re-run of 1,000 documents completes within cost budget. Cache hit rate above 90% on repeat runs.

### Phase 8 — Predictor

LightGBM. `max_depth ≤ 4`, high `min_child_samples`, L1 and L2 regularization, `feature_fraction ≈ 0.6`, early stopping on a purged validation fold. Ensemble across time windows only — no model stacking, no architecture search.

Output is a cross-sectional rank, never a price or a return magnitude.

**Gate:** Purged K-fold CV with embargo implemented and unit-tested for correct fold boundaries. Information coefficient reported with t-statistic. Every configuration tried is appended to `TESTING_LEDGER.md` — this ledger feeds the Deflated Sharpe calculation in Phase 10 and its completeness determines whether that number is honest.

### Phase 9 — Portfolio and costs

Covariance via Ledoit-Wolf shrinkage. Optimizer in cvxpy: maximize expected return minus risk penalty **minus explicit turnover penalty**, subject to sector neutrality, beta neutrality, position cap 2%, sector cap 20%, full-investment constraint.

Cost model: half-spread + commission + square-root market impact scaled by order size over ADV + borrow cost on shorts.

**Gate:** Optimizer solves reliably across historical dates without infeasibility. Turnover penalty demonstrably reduces realized turnover in backtest. Cost model calibrated against paper fills once Phase 11 exists — until then, conservative defaults, clearly flagged.

### Phase 10 — Validation framework

**Build this with maximum care. Every other phase depends on it being correct.**

- Purged K-fold with embargo
- **Combinatorially Purged Cross-Validation** producing a distribution of out-of-sample Sharpe ratios rather than a point estimate
- **Deflated Sharpe Ratio**, using the full trial count from `TESTING_LEDGER.md`
- **Probability of Backtest Overfitting**
- Walk-forward analysis
- Benchmark comparison against buy-and-hold index, always shown alongside every strategy result

Every reported metric is net of costs. Every metric carries a confidence interval. No point estimate is ever displayed alone in the UI.

**Gate:** Framework reproduces known results on synthetic data with injected signal of known strength — and correctly reports near-zero signal on pure noise. This second test is the critical one. If your framework finds alpha in random data, it is broken and everything downstream is fiction.

### Phase 11 — Execution (paper only)

IBKR adapter against a paper account. Order management with idempotency keys. Position reconciliation on every cycle. VWAP/TWAP slicing. Kill switch triggering on: drawdown breach, stale data, reconciliation mismatch, or manual operator action.

A configuration flag for live trading must not exist. The adapter hard-codes the paper endpoint.

**Gate:** Full cycle runs end-to-end against paper. Reconciliation catches an artificially injected mismatch. Kill switch halts within one cycle when triggered.

### Phase 12 — Monitoring

Live-versus-expected tracking against the CPCV distribution. Feature drift via PSI. Extraction-quality drift on the golden set. Automated alerts. Auto-halt when live performance falls outside the expected distribution.

**Gate:** Injected drift is detected. Injected performance deviation triggers halt.

## 6. OPERATOR DASHBOARD

The dashboard is not a reporting layer bolted on at the end. It is the control surface. Build it incrementally alongside the backend phases.

### 6.1 Overview

Portfolio value, live-versus-expected chart with CPCV confidence bands, current drawdown against limit, system health tiles per component, active alerts, next scheduled job, spend today against cap.

### 6.2 Data Health

Per-source coverage heatmap by date, gap detection with severity, staleness monitor, ingestion run history, manual re-sync trigger, quality metrics over time.

### 6.3 Universe

Current constituents with entry and exit dates, size and turnover history, filter-impact waterfall showing how many names each screen removes, point-in-time browser to inspect the universe as of any past date.

### 6.4 Features

Feature catalog with definitions, availability lags, and coverage. Correlation heatmap. Rolling IC per feature. Distribution plots. Enable/disable toggles that write to config and require a re-run to take effect — never silently mutate a live model.

### 6.5 Agents and Extraction

**This is the page the operator lives in. Build it properly.**

- **Provider registry:** add, edit, rotate, delete API keys per provider. Keys encrypted at rest with a key-encryption key from environment. Display permanently masked (`sk-...4f2a`) with no reveal endpoint. "Test connection" button issuing a minimal live call and reporting latency and status
- **Per-task model assignment:** each extraction task independently assigned a provider, model, temperature, max tokens, and timeout. Changing an assignment creates a new configuration version rather than mutating the current one
- **Prompt management:** full version history per prompt, side-by-side diff between versions, golden-set score attached to each version, one-click rollback. Prompts are content-addressed; a prompt change invalidates the cache for affected documents automatically
- **Ensemble configuration:** which models vote, aggregation method, disagreement threshold that flags a document for review
- **Cost governance:** daily and monthly caps per provider, live spend gauges, projected month-end spend, hard-stop behavior configurable between halt and degrade-to-cheaper-model
- **Quality monitoring:** golden-set score trend per prompt version, contamination-probe divergence over time, extraction latency distribution, error and retry rates
- **Document inspector:** pick any document, see the anonymized text actually sent, each model's raw response, the aggregated value, and the disagreement score

### 6.6 Models

Training run history with full config, feature importance via SHAP with an explicit warning about its instability on correlated features, IC and t-statistic per run, purged-CV fold visualization, model registry with promote and archive actions.

### 6.7 Backtests

Backtest explorer. Equity curve against benchmark. **CPCV Sharpe distribution as a histogram with the point estimate marked on it** — this visualization matters more than any other in the application, because it is what stops a single lucky path from being mistaken for an edge. Deflated Sharpe, PBO, drawdown analysis, turnover, cost decomposition as a waterfall, per-year attribution, run comparison.

Every backtest view displays the trial count from the testing ledger alongside the result.

### 6.8 Portfolio

Current and target positions, drift from target, sector and factor exposures, planned rebalance trades with estimated cost, constraint-binding indicators showing which limits are active.

### 6.9 Execution

Order blotter, fill history with slippage against arrival price, reconciliation status, cost-model calibration comparing predicted against realized, kill-switch status and manual trigger.

### 6.10 Monitoring

Drift dashboards, alert history with acknowledgement, halt history with cause.

### 6.11 Settings and Audit

System configuration, scheduler management, backup status. **Immutable audit log** of every configuration change: who, when, what changed, previous value, new value. Config changes are events, not mutations.

## 7. SECURITY

- Keys encrypted at rest via Fernet, KEK from environment, never from the database
- No endpoint returns a full key under any circumstance
- Structured logging with automatic redaction of anything matching key patterns
- CSRF protection, rate limiting on all mutating endpoints
- Parameterized queries only
- Dependency scanning in CI
- `.env.example` committed; `.env` in `.gitignore` and verified by a pre-commit hook

---

## 8. QUALITY BAR

- Type coverage 100% on backend, `mypy --strict`. TypeScript strict with no `any`
- Test coverage ≥ 85% backend, ≥ 70% frontend
- Hypothesis property tests on: bitemporal layer, label construction, optimizer constraints, cost model
- Integration tests using Testcontainers against real Postgres
- Playwright end-to-end on critical dashboard paths
- Every public function has a docstring stating what it does, its units, and its assumptions
- Financial functions state units explicitly — basis points versus percent versus fraction is the most common bug class in this domain and it is silent

## 9. FORBIDDEN BEHAVIORS

Read this section again before every session.

1. **Never fabricate data.** No synthetic data presented as real, ever
2. **Never stub for appearance.** A function that returns a plausible value without doing the work is worse than one that raises `NotImplementedError`
3. **Never skip or weaken a test to pass a gate**
4. **Never invent an API.** If you are unsure whether an endpoint or parameter exists, check the documentation or write it to `BLOCKERS.md`
5. **Never enable live trading.** No flag, no environment variable, no commented-out code
6. **Never report a gross return**
7. **Never delete from `TESTING_LEDGER.md`.** Deleting failed experiments is how backtest overfitting becomes invisible
8. **Never proceed on a guess.** Ambiguity goes to `BLOCKERS.md`
9. **Never build outside scope.** Ideas go to `BACKLOG.md`
10. **Never claim a phase complete when its gate has not passed**

## 10. SESSION PROTOCOL

**Start:** read `PLAN.md`, `PROGRESS.md`, `BLOCKERS.md`. State which task you are picking up and why.

**During:** one task at a time. Write the test first. Implement. Run the full suite, not just the new test. Commit. Update `PROGRESS.md`.

**End:** update all state files. Write a session summary to `PROGRESS.md` covering what was completed, what failed, what is blocked, and the exact next task. Leave the repository in a state where `docker compose up` works and all tests pass.

If you hit a blocker, do not stop working — check whether an independent track exists and move to it. Phases 3 and 7 are largely independent of Phases 5 and 6, for example.

## 12. WHAT SUCCESS LOOKS LIKE

A system where every number displayed is honest, every result is reproducible, every experiment is logged, and the validation framework is trusted enough that a negative result is believed rather than explained away.

The hardest part of this project is not making a strategy look profitable. It is building infrastructure rigorous enough that you know when it isn't.
